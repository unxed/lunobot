# Модуль: Релизы (§ 7.7)

Часть [инструкции Лунобота](../LUNOBOT.md), вынесенная из ядра без изменения смысла. Читай его целиком Лунобот-1 — на ретро круга (порог релизов) и перед любым тегом или релизом. Правила ядра действуют и здесь; «§ N» ведут в раздел с этим номером в ядре или в модуле (таблица модулей — в начале ядра).

### 7.7 Релизы

Пользователь получает работу не только из `main`, но и из релизов, поэтому проекты из `INDEX.md` выпускают версии
по вехам. Релизы и теги версий создаёт **только Лунобот-1**; Лунобот-2 этот раздел пропускает. Строка `Релизы:`
паспорта со своим правилом (vtui: тег после каждого мержа — иначе f4 не подтянет исправление) сильнее порогов ниже.

**Механизм — из паспорта.** Строка `- Релизы: <тег v* → workflow | ручной gh release | нет>; схема: <vX.Y.Z | …>;
<плавающие релизы, не трогать>`. Нет строки — один раз посмотри на GitHub (`git ls-remote --tags --refs
--sort=-v:refname <url>`, `gh api 'repos/<r>/releases?per_page=5'`, workflow с `on: push: tags` или nightly в
`.github/workflows`) и запиши её в паспорт коммитом учёта. Схему продолжай существующую; тегов версий нет —
semver с `v0.1.0`; `v1.0.0` — только по слову владельца. Плавающие релизы (`nightly` f4, dn) не трогай; если
`Latest` сейчас у плавающего, новый релиз создавай с `--latest=false`.

**Когда.** Проверка — на ретро круга (§ 4 п. 6), одной командой по всем проектам с `- Релизы:` в паспорте:
`python3 release_due.py` (только чтение, код 0): последний тег версии из `git ls-remote --tags --refs --sort=-v:refname`
(плавающие `nightly` и т. п. пропускает; список релизов — не список тегов: 21-10-2026 `releases?per_page=10` дал zipper
v0.1.167 при теге v0.1.178), число коммитов с `Touch:` в `compare <тег>...main` по всем страницам (одна страница
отдаёт не больше 250 коммитов) и возраст тега; по порогу (б) печатает «кандидат на релиз». Кандидат на релиз, если с прошлого тега в `main` есть хотя бы одно: (а) веха — закрыт зонтичный или многошаговый
тикет (последняя часть в `main`), новая заметная пользователю возможность (`enhancement` с «Пробуйте!»), пять и
больше исправленных `bug`; (б) накопление — 20 и больше коммитов с `Touch:` либо 14 суток и хотя бы один такой
коммит. Сам релиз — работа ниже § 5 п. 2–4 и тикетов приоритета 1–2, выше § 5 п. 6. Против голодания: кандидат,
чей порог (а) или (б) выполнен 7 и больше суток назад (по дате первого коммита сверх порога) и без живого захвата
«релиз», получает следующий свободный слот воркера раньше свободных блоков `OWNER_QUEUE.md` (но не раньше § 5 п. 2–3
и уже захваченных поручений): иначе в круге с одним воркером (§ 4, потолок (б)) долгие блоки «вести …» его вытесняют
всегда (21-10-2026: f4 — 118 коммитов с `Touch:` с v0.3.0-beta от 26-09, dn — 111 с v2.20-alpha.1 от 08-10).

**Захват** (§ 3 п. 12): `взял кастомную задачу «релиз <owner/repo> <тег>» по § 7.7 [urgent: по § 7.7 — релиз,
без ветки и PR]`; живая строка «релиз <owner/repo>» с любым тегом — проект занят.

**Стабильный срез** — sha, у которого все сразу: (1) он в `main` (не staging, не ветка поезда); (2) все
обязательные проверки паспорта на ЭТОМ sha зелёные по check-runs коммита (§ 5 п. 3; у fast-forward поезда — его
полная матрица на том же sha, отменённый затем прогон `main` не мешает) — середина поезда полной матрицы не
проходила и не годится; (3) нет открытого `bug` приоритета 1–2 (§ 5.1), появившегося после прошлого тега, и нет
такого `в пути` (дешевле дождаться поезда); `bug` в `проверяют`/`решён` (исправление уже в `main` на срезе) срез не
блокирует и идёт в «Исправления» (unxed/f4#2035, unxed/f4#1861); более старый открытый p1–2 — «сознательно оставленный»: он
перечисляется в заметках разделом «Известные проблемы» со ссылкой; (4) ни один `status/*.md` не говорит, что
влитая часть без следующей ломает формат, миграцию или протокол. Подходящий срез — самый свежий такой sha.

**Выпуск.** Тег, который запускает тяжёлую матрицу, — это полный прогон: перед пушем проверь потолок (а) § 4;
занят — отложи до следующего круга, не жди. Исключение — кандидат с голоданием (порог (а) или (б) выполнен 7 и
больше суток назад, абзац «Когда»): его тег потолок (а) не ждёт, как срочная работа § 4 («для срочной работы эта
проверка не блокирует»), но по аккаунту одновременно не больше одного такого тега и не вместе со вторым тегом
(21-10-2026 10:34Z `tick-all` нарезал поезд unxed/f4#2127, и релизы f4 — 970 коммитов с `Touch:` после v0.3.0-beta от
26-09 — и dn — 125 после v2.20-alpha.1 от 08-10 — снова отложены: поезд f4 режется почти в каждом круге, и правило
против голодания не срабатывало; тег dn запускает `dn.yml`, `dn-linux.yml`, `dn-windows.yml` по `tags: ['**']`, так
что лёгким не считается). Аннотированный тег `git tag -a <тег> -m "<тег>" <sha>`, `git push
origin <тег>`, затем `gh release create <тег> --verify-tag --title <тег> --notes-file <файл>` (если релиз создаёт
сам workflow по тегу — `gh release edit <тег> --notes-file <файл>` после него). Заметки — на языке существующих
релизов (нет — README проекта): «Новое», «Исправления» (по строке на тикет из `Проблема:`/`Исправление:` коммитов
диапазона, у PR без трейлеров — заголовок PR, `#N` без владельца — § 2), «Известные проблемы»; подпись по § 9.
Файл пиши по § 2, перед отправкой `python3 gh_post.py check <файл>` (код 0), после — прочти тело обратно
(`gh api repos/<r>/releases/tags/<тег> --jq .body`) и сравни с файлом; не совпало после одной правки — среда
сломана, жалоба (§ 12). Затем сними захват.

**Пост-фактум.** Когда паспорт впервые получает строку `Релизы:` (или по слову владельца), Лунобот-1 одним шагом
просматривает историю `main` после последнего тега версии (влитые поезда и PR, закрытые зонтичные тикеты) и
находит места, где по порогам выше релиз полагался, а тега нет. Срез выбирается по тем же критериям на ТОТ момент:
check-runs того sha зелёные (нет данных — не тот срез), открытые тогда `bug` — по `created_at`/`closed_at` и
меткам. Версия обязана встать между соседними тегами (меньше всех последующих); свободного номера нет — веху
пропусти. Релиз — с `--latest=false`, в заметках строка «Выпущен пост-фактум <дата UTC> на срезе от <дата>».
Пуш тега, запускающего workflow, — по потолку (а) § 4, не больше одного пост-фактум тега за круг.
Существующие теги и релизы без слова владельца не переписывай, не двигай и не удаляй.
