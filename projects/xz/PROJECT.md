# xz

- Код: https://github.com/unxed/xz
- Форк ulikunitz/xz (Go-библиотека LZMA/LZMA2/.xz), от которой зависят
  unxed/tar, unxed/zip, unxed/zipper (через go.mod), а через них — f4
- Задачи: тикеты и PR этого же репозитория, а также задачи из зависимых
  репозиториев (например unxed/zipper), которые по факту требуют правки
  здесь — тогда PR открывается сюда, а в тикете зависимого репозитория
  оставляется `Touch owner/repo#N`
- PR: туда же, ветка -> PR -> мерж в main
- Зависимости: нет (сама является зависимостью tar/zip/zipper)
- Покрытие: не проверялось, уточнить прежде чем брать задачи по покрытию
- Язык общения: английский (upstream-стиль репозитория)
- CI: `go-test-platforms.yml` (go test -race ./... на Linux/Windows,
  GOARCH=386 без -race), `coverage.yml`, `codeql.yml` — все на
  push/pull_request в master
- Особенности: у библиотеки нет понятия "уровня сжатия" в духе -0..-9 на
  уровне LZMA-энкодера — WriterConfig/Writer2Config статичны на весь
  поток (Properties/DictCap/Matcher), сам энкодер — greedy-матчер без
  nice-length/depth. Единственный "preset" — это `-0`..`-9` у CLI gxz
  (cmd/gxz), который просто маппится в фиксированный DictCap на весь
  файл (cmd/gxz/file.go)
- unxed/zipper#20 (VBR-эвристики для LZMA), часть 2/3: `Writer2Config.AdaptiveEffort`
  (по умолчанию `false`) — единственная точка, где Matcher теперь всё же
  меняется внутри потока, per-block, а не статично на весь Writer2Config.
  На каждой границе параллельного блока Writer2 (которая уже совпадает с
  началом новой последовательности LZMA2-чанков) считается
  `internal/redundancy.EstimateRedundancy` по сырым байтам блока (см.
  часть 1/3, PR #2, смержен); при `>= adaptiveEffortThreshold` (0.5, не
  тюнинг — это часть 3) для блока используется BinaryTree вместо
  сконфигурированного Matcher, иначе HashTable4. DictCap/Properties эта
  часть не трогает (посчитано либо слишком дорогим менять на лету
  (BinaryTree аллоцирует узлы пропорционально DictCap), либо не нужным
  для честной демонстрации, что метрика реально влияет на параметры).
  Реализация — `lzma/writer2.go`: `worker()` держит по одному
  `seqWriter2` на алгоритм, что реально понадобился (кэш
  `map[MatchAlgorithm]*seqWriter2`), строя запись под альтернативный
  алгоритм лениво, только когда `AdaptiveEffort` реально выбрал его для
  какого-то блока. При `AdaptiveEffort: false` в кэше всегда ровно одна
  запись под сконфигурированным `Matcher` — поведение полностью
  совпадает с тем, что было до этой опции.
