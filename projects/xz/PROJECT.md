# xz

- Код: https://github.com/unxed/xz
- Форк ulikunitz/xz (Go-библиотека LZMA/LZMA2/.xz), от которой зависят
  unxed/tar, unxed/zip, unxed/zipper (через go.mod), а через них — f4
- Задачи: тикеты и PR этого же репозитория, а также задачи из зависимых
  репозиториев (например unxed/zipper), которые по факту требуют правки
  здесь — тогда PR открывается сюда, а в тикете зависимого репозитория
  оставляется `Touch owner/repo#N`
- PR: туда же, ветка -> PR -> мерж в main
- Режим публикации: PR (простой маршрут, `lunobot/staging`/`quick.yml` нет)
- Отладка GitHub CI: да (компилируемый Go-проект; локально — только
  `gofmt -l`, тестирование/vet/бенчмарк — через `sandbox.yml`, § 7.5)
- Зависимости: нет (сама является зависимостью tar/zip/zipper)
- Покрытие: не проверялось, уточнить прежде чем брать задачи по покрытию
- Язык общения: английский (upstream-стиль репозитория)
- CI: `go-test-platforms.yml` (go test -race ./... на Linux/Windows,
  GOARCH=386 без -race), `coverage.yml`, `codeql.yml` — все на
  push/pull_request в master
- Особенности: у библиотеки нет понятия "уровня сжатия" в духе -0..-9 на
  уровне LZMA-энкодера — WriterConfig/Writer2Config статичны на весь
  поток (Properties/DictCap/Matcher), сам энкодер — greedy-матчер без
  nice-length/depth. Единственный "preset" — это `-0`..`-9` у CLI gxz
  (cmd/gxz), который просто маппится в фиксированный DictCap на весь
  файл (cmd/gxz/file.go)
- `lzma/bintree.go`: `binTree.add`/`binTree.remove` были без ограничения
  глубины обхода — на периодичных/избыточных данных (короткий период
  относительно 4-байтового слова матчера, например `bytes.Repeat`
  паттерна) почти все вставки схлопывались на нескольких вырожденных
  цепочках, давая O(n²) по размеру блока. Именно это повесило
  `TestWriter2_AdaptiveEffortRoundtrip` на 10-минутный таймаут CI на
  Linux и Windows (unxed/zipper#32). Исправлено в PR unxed/xz#5
  (смержен, `a6dd933`/`7adda47`): обе функции капнуты на
  `maxTreeDepth = 48` (по образцу liblzma `depth_limit = 16 +
  niceLen/2`, где niceLen — `nAccept` пакета, 64). За пределами глубины
  дерево перестаёт быть строго упорядоченным, но это не риск для
  корректности — `match()` в `NextOp` всегда перепроверяет кандидата по
  реальному буферу, теряются только некоторые потенциальные совпадения.
  Регрессия: `TestBinTree_PeriodicInsertBounded` (bintree_test.go, 30s
  таймаут) и `TestWriter2_BinaryTreePeriodicRoundtrip` (round-trip,
  60s таймаут) на том же 27-байтовом периодичном паттерне из тикета.
  CI на master после мержа зелёный и быстрый (~2 мин Linux job,
  ~1м41с Windows job — далеко от прежнего 10-минутного таймаута).
- unxed/zipper#20 (VBR-эвристики для LZMA): `Writer2Config.AdaptiveEffort`
  и `internal/redundancy` были реализованы (части 1-3, PR #2/#3), но
  **полностью откачены** PR unxed/xz#4 (`0680850`, смержен 27-09-2026,
  до фикса `bintree.go` выше) — бенчмарк не показал измеримой выгоды
  по коэффициенту/скорости сжатия над статичным `Matcher` даже до того,
  как обнаружился O(n²)-баг. На `master` сейчас `Writer2Config` не
  содержит `AdaptiveEffort`/`selectAdaptiveMatcher` вовсе. Сам тикет
  #20 остаётся открытым как продуктовый вопрос — стоит ли переделывать
  VBR-эвристики заново поверх уже исправленного `bintree.go` — это
  решение не техническое, за владельцем.

Этот паспорт — то место, где живут отличия проекта от остальных. Не хватает ответа
на вопрос, который встал в работе, — дополни паспорт вместе с правкой по задаче.
