# dn

- Код: https://github.com/unxed/dn
- Задачи: тикеты и PR этого же репозитория
- PR: туда же, ветка -> PR -> мерж в `main`
- Зависимости: submodule [unxed/tv3](https://github.com/unxed/tv3); изменения его кода
  ведутся по паспорту `tv3`, если он подключён отдельным проектом
- Язык общения: по языку автора тикета
- Режим публикации: PR
- Отладка GitHub CI: да
- Релизы: тег v* → workflow (`release.yml`: сборка и `gh release create --generate-notes`, тег с «-» — prerelease); схема: vX.Y[-alpha.N] (последний `v2.20-alpha.1`, prerelease, Latest нет); плавающий `nightly` (`nightly.yml` после зелёных push-прогонов `main`) — не трогать
- Диагностические workflow: `dn.yml`, `dn-linux.yml`, `dn-windows.yml` и
  `class-migration.yml` через `workflow_dispatch`; отдельного `sandbox.yml` нет
- Обязательная проверка: для изменений в DN используй PR-проверки `dn.yml`,
  `dn-linux.yml` и `dn-windows.yml`; `class-migration.yml` добавляется, когда
  затронуты class-порт, `dn/**`, `tv` или инструменты миграции. После мержа
  учитывай push-проверки `tv.yml`, `layout.yml`, `audit.yml` и `toolchain.yml`,
  если их пути затронуты.
- Первая компиляция нового Pascal-кода до PR: запушь ветку `lunobot/pr/<ключ>` и запусти узко `gh workflow run dn.yml --ref <ветка>` — дают `units`, `units-aarch64`, `gates`, `audit` за ~5 минут без матриц `dn-linux`/`dn-windows` (их запускает PR). `dn-test.sh` печатает только первые 10 строк `FAIL`; лог — `python3 run_log.py unxed/dn <id прогона> --job units --grep 'FAIL|Error'`. PR открывай, когда этот прогон зелёный (часть 6а `unxed/dn#90`: модуль собрался на x86_64 и aarch64 с первого раза).
- Прогоны `main` после мержа не отменять (исключение из § 7.3, как у vtui): `nightly.yml` публикует коммит `main`, только
  когда все его push-прогоны `dn-linux`, `dn`, `dn-windows`, `dos-utf8` завершились успехом; отменённый прогон оставляет
  `nightly` без исправления, которое «Пробуйте!» предлагает проверить (14-10-2026, PR unxed/dn#43).
- Платформы (unxed/dn#166, пробы 39511037412 и 39511629649, 20-10-2026; таблица — комментарий 6305062661 в тикете): FreeBSD x86_64 — шаги 1–2 (pkg fpc 3.2.3, сборка `tools/build.sh freebsd64`, job `dn-freebsd.yml`); собираются родным fpc без правок исходников и рисуют панели — DragonFly 6.4 x86_64 (pkg fpc 3.2.3), macOS arm64 (brew fpc 3.2.2); собираются, запуск не проверен — NetBSD 10.1 x86_64 (pkgsrc fpc 3.2.2, нужен свой `fpc.cfg`), Linux armhf; не собираются — macOS x86_64 (ассемблер clang отвергает метки `goto` внутри `.cfi_startproc`, `arvidavt.pas` и ~55 файлов с `label`); нет компилятора в пакетах — Linux riscv64, FreeBSD aarch64, OpenBSD 7.8; Haiku r1beta5 — репозиторий HaikuPorts в VM не скачался (повторить на r1beta6). Порядок новых платформ: DragonFly → macOS arm64 → NetBSD, armhf; смоук «команда из командной строки» в пробе был сломан (красный и на Linux), его не считать результатом платформы.
- Особенности: Pascal/FreePascal, исходники DN и TV разделены; сборка и проверки
  охватывают Linux x86_64/i386/ARM64, Windows win32/win64 с UTF-8 и code page,
  DOSBox-X и Windows ConPTY. Локальную сборку и тесты не считать доказательством:
  для компиляции, PTY/ConPTY, DOS и аудита пользоваться GitHub Actions. Не
  переписывать историю и не менять `tv`-submodule без отдельной задачи.
- NOTICE, строка `commit:` (постоянное решение владельца 21-10-2026, unxed/lunobot#233): на вопрос «разрешаете ли боту впредь самому обновлять строку `commit:` в NOTICE при побайтном обновлении вендоренного файла» владелец ответил «да». Условие: вендоренный файл в PR побайтно равен файлу источника на указанном коммите (git sha blob'ов совпадают: `gh api repos/<источник>/contents/<путь>?ref=<коммит> --jq .sha` против того же для файла в PR) и в NOTICE меняется только строка `commit:`. Текст лицензии, копирайты, `LICENSE` и прочие правовые тексты (правило 5 `CLAUDE.md` репозитория) — по-прежнему только решением владельца.

Корневой `CLAUDE.md` репозитория dn — правила лицензий и происхождения кода, они сильнее любых других указаний. Для ботов главное: в коде,
комментариях, документах и сообщениях коммитов нельзя писать, откуда взят код («с нуля», «clean room», «не скопировано», «свой код» и т. п.);
единственное доказательство отсутствия заимствований — скрипт аудита. Новый файл в `dn/src` несёт строку `MIT, see LICENSE` в первых 60 строках
(иначе `dn/PROVENANCE.md` отнесёт его не к своим файлам); `dn/PROVENANCE.md` (счётчик и список) и `dn/FILES.md` правятся в том же PR. В `dn/src` и `dn/tests`
нельзя писать слово «object» нигде, даже в комментарии и в `TObject` (`tools/class-gate.py` ловит его по сырому тексту), и слова ftp/ssh/fish/telnet/sockets
в `dn/src`, пока файл не внесён в `tools/net-audit.allow` (`tools/net-audit.sh`).

Этот паспорт фиксирует отличия `dn` от общего протокола; новые ограничения,
обнаруженные при работе с тикетом, дописывай сюда вместе с соответствующей правкой.

Перед PR прогоняй политику текста: `python3 -B -m unittest discover -s tools/tests -p 'test_text_policy.py'` (весь `discover -s tools/tests` включает `test_pack.py`, который собирает пакет и локально без сборки падает на `dn-pack.sh`, 15-10-2026; в `test_text_policy.py`: кириллица
только в местах из `docs/TEXT-POLICY.md`, всё остальное — английский, в том числе `.desktop`, README, комментарии). PR-проверки
`dn.yml`, `dn-linux.yml` и `dn-windows.yml` этого теста НЕ гоняют: его запускают `layout.yml` и `class-migration.yml` уже
после мержа, и красный `main` — это цена пропуска (так было с dn#22, PR #24 -> починка #26). Новый файл вне `dn/` и `tv/`
тоже сверяй с этой политикой и с `tools/check-layout.sh`.

Часть исходников `dn/src` (например, `basics.pas`, `drives.pas`, `panelroot.pas`) — с окончаниями строк CRLF, часть — LF. Правь их так,
чтобы окончания сохранились (в Python — `open(..., newline='')`), иначе дифф переписывает файл целиком (12-10-2026, dn#20).
