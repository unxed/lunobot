# unxed/keytrans#1 — встроить xkeyboard-config для полной X11-независимости

Статус: первый срез (оценка размера) сделан и отправлен, PR
https://github.com/unxed/keytrans/pull/8 (в пути, только докстраница +
скрипт измерения, функционального кода нет). Владелец в комментарии к
тикету прямо попросил именно это как первый шаг: «оценить, насколько это
утяжелит собранную версию (можно использовать сжатие)» — поэтому этот
круг не пытался сразу делать полную реализацию встраивания, а закрыл
именно заданный владельцем вопрос.

## Что сделано

- `scripts/measure-xkeyboard-config-size.sh` (новый, в PR #8) —
  воспроизводимый замер размера `xkeyboard-config`: полное дерево и
  минимальный набор (без `geometry/`, без GUI-каталогов `.xml`/`.lst`,
  без legacy-дубликата `base`/`xorg`, только `evdev`).
- `docs/embed-xkeyboard-config.md` (новый, в PR #8) — числа + два
  архитектурных вывода.
- Комментарий с теми же числами и выводами оставлен прямо в тикете:
  https://github.com/unxed/keytrans/issues/1#issuecomment-5877724161

## Числа (Ubuntu xkb-data 2.41-2ubuntu1.1)

| Набор | raw | xz -9 |
|---|---|---|
| Полное дерево xkeyboard-config | 3.6 МБ | 339 КБ |
| Минимальный (без geometry/xml/lst/base) | 2.4 МБ | 287 КБ |

Ожидание в тикете (~200 КБ сжато, ~50 КБ RAM) в целом верно по порядку
величины для сжатого размера (339/287 КБ — не так далеко от 200 КБ,
разница объясняется тем, что это *все* раскладки апстрима, а не
курируемое подмножество), но **RAM-оценка (~50 КБ) ошибочна примерно на
два порядка**: парсеру `xkb-go` нужны распакованные данные (2.4–3.6 МБ),
а не сжатый at-rest размер — это явно отмечено в комментарии к тикету и
в докстранице как корректировка, а не как критика постановки задачи.

## Архитектурные находки (важны для следующего шага)

1. `xkb-go` (`context.go`/`rules.go`) читает XKB-файлы через
   `os.Open`/`os.ReadFile` по реальным путям ФС (`/usr/share/X11/xkb` и
   т.п.), не через `fs.FS`/`embed.FS`. Значит `go:embed` не подключается
   напрямую — нужен шаг «распаковать embed.FS в кэш-каталог (например
   `os.UserCacheDir()`, с хэшем содержимого, чтобы не распаковывать
   повторно) → `Context.PrependIncludePath(dir)`». Публичного API
   `xkb-go` (`NewContext`, `ContextNoDefaultIncludes`,
   `PrependIncludePath`) для этого достаточно — **правка самой `xkb-go`
   не нужна** для этой части.
2. Флаг `xkb.ContextNoEnvironmentNames` задокументирован как влияющий на
   чтение `XKB_DEFAULT_RULES/MODEL/LAYOUT/VARIANT/OPTIONS`, но по коду
   `xkb-go` (grep по репозиторию) это нигде не реализовано — флаг
   сейчас no-op. Значит источник RMLVO без X11-соединения (собственно
   смысл тикета — независимость от X11) придётся строить в самом
   `keytrans` (например чтение `XKB_DEFAULT_*`/явного конфига как
   фоллбэк, когда нет `_XKB_RULES_NAMES`), а не полагаться на то, что
   это уже есть в библиотеке.

## Не сделано (следующий шаг, не в рамках этого RUP-хода)

- Решение «встраивать все раскладки мира (~290-340 КБ) или курируемое
  подмножество (латиница+кириллица+популярные)» — явно не принято в
  этом шаге, оставлено как продуктовый вопрос.
- Сам `go:embed` + распаковка в кэш-каталог + `PrependIncludePath`
  wiring в `backend_purexkb.go` (или новый бэкенд).
- Источник RMLVO без X11 (переменные окружения/конфиг) — нужен, чтобы
  embed вообще был достижим без `_XKB_RULES_NAMES`.
- Выбор алгоритма сжатия для реализации: `xz`/`zstd` дают лучший
  коэффициент, но добавляют зависимость; `compress/flate` из stdlib —
  без новой зависимости, но хуже сжимает. Не бенчмаркалось в этом шаге.
