# keytrans#2 — Core X11 group mapping на 3+ раскладках

PR: https://github.com/unxed/keytrans/pull/7 (ветка
`lunobot/91d86915909d88ed7991a74c/lunobot-3/2`), ждёт зелёного прогона
`Coverage` и мержа по § 5 п. 3.

## Причина бага

`backend_corex11.go` — эвристический фоллбэк без CGO/FFI (последний в цепочке
`x11_factory.go`, до него пробуются `xkbgo-x11`, `libxkbcommon`, `libX11-XIM`,
`purexkb`, `dynamicxkb`, `xkbcomp`). Он уже правильно запрашивал активный
XKB-group index через `XkbGetState` (0-3), но `lookup()` умел превращать
этот индекс в смещение в плоском массиве keysym'ов, который отдаёт
`GetKeyboardMapping`, только для ровно двух групп: старая 8-символьная
чересстрочная раскладка (legacy pre-XKB core-протокол) или зашитый разбор
"2-широкий блок для групп 0-1, 4-широкий блок для всего остального" — эта
ширина никогда не бралась из фактического числа настроенных групп. При
3+ раскладках (например английская+русская+французская) вычисленные
смещения для третьей и далее группы были попросту неверными.

## Фикс (влит в PR #7)

- Новый запрос `queryXKBNumGroups` (сырой XKB `GetControls`, opcode 6,
  по образцу уже существовавшего в файле сырого `XkbGetState`) плюс
  переиспользование уже протестированной `xkb.ParseX11GetControlsReply` из
  `github.com/unxed/xkb-go` (уже зависимость, уже используется тем же
  способом в `x11/x11.go` этой библиотеки для `backend_xkbgo_x11.go`) —
  вместо ручного разбора ещё одного сырого ответа.
- Когда сервер сообщает 3 или 4 группы и `symsPerKeycode` делится на это
  число нацело, `lookup()` использует равномерную раскладку блоков
  (`width = symsPerKeycode/numGroups`, группа `g` начинается с `g*width`) —
  именно так core-протокол-совместимая проекция XKB-раскладки реально
  устроена для N>=3 групп, в отличие от старой пары эвристик, рассчитанных
  только на 2 группы.
- Для 2 групп и для случая, когда число групп неизвестно (нет XKB-расширения)
  или не делится нацело на `symsPerKeycode` (повод не доверять ему вслепую) —
  поведение побайтово не изменилось: старые эвристики остаются as is.
- Число групп перечитывается на том же цикле в 1 секунду, на котором и так
  идёт периодическая перезагрузка keymap — переключение с 2 на 3+ активных
  раскладки на лету (`setxkbmap`) подхватывается без перезапуска процесса.
- Юнит-тесты (мок-транслятор, без реального X11-соединения, тот же паттерн,
  что и остальные тесты `backend_corex11_test.go`): 3 группы без AltGr,
  3 группы с AltGr (12 символов/keycode), 4 группы, и защитный фоллбэк при
  несовпадении `numGroups`/`symsPerKeycode`.

## Что НЕ покрыто — возможный следующий шаг

Формула `width = symsPerKeycode/numGroups` проверена только юнит-тестами на
смоделированных данных (в этом окружении нет живого X-сервера для проверки
`KEYTRANS_BACKEND=corex11` вживую с реально настроенными 3+ раскладками —
см. пункт "Test plan" в PR #7). Это не сужение диагноза, а честно
непроверенное вживую предположение о протокольном поведении реальных
X-серверов/драйверов; сам класс проблемы (что XKB core-protocol-compat
маппинг раскладывает группы равными блоками для N>=3) хорошо задокументирован
и согласуется с тем, как этот же keytrans уже парсит `GetControls`/`GetMap`
в `xkb-go` для `backend_xkbgo_x11.go`, но не проверен вручную на реальном
сервере в рамках этого шага. Если после мержа появятся отчёты пользователей о
неверном маппинге на конкретных драйверах/раскладках — это следующий тикет
или комментарий сюда, не повод откатывать этот PR: он строго не хуже старого
поведения (для <3 групп ничего не поменялось) и явно лучше для 3-4 групп в
покрытых юнит-тестами случаях.
