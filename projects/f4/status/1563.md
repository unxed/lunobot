## isoimg / wasi-sdk разведка — ЗАВЕРШЕНА, успех

Основная логика isoimg (без `isz/*` — GPL-2 AES) компилируется и линкуется под
wasm32-wasip1 (wasi-sdk-34) в рабочий reactor 309 446 байт. Компактный
compat-слой (`compat/windows.h`, ~400 строк) поверх POSIX — не редактируя
исходники Observer.

**Подтверждено бесплатным** (без единой правки): `__stdcall`/`CALLBACK`
(в wasm нет calling conventions), `#pragma pack(1)`, `HANDLE`/`FILETIME`/`GUID`
как POD в ABI-структурах.

**Реальная находка, НЕ бесплатная:** `wchar_t` у wasi-sdk по умолчанию 32-бит
(как на Linux), а протокол Observer собран под 16-бит (UTF-16). Нужен
`-fshort-wchar`, но тогда весь набор wide-string функций из `libc.a` wasi-sdk
непригоден (сам libc собран с обычным 32-бит `wchar_t`) — пришлось написать
СВОИ реализации wide-функций. Это единственная содержательная часть compat-слоя,
специфичная для Observer (у colorer4go такой проблемы не было).

**Следующие шаги (не в этом заходе):**
1. Настоящая семантика UTF-8↔UTF-16/кодовых страниц (сейчас грубые заглушки).
2. Мост Go↔wasm ABI для `module_cbs` (таблица указателей на функции в структуре,
   а не плоские C-экспорты как у colorer4go) — отдельная, не исследованная задача.
3. Гигиена макросов `min`/`max` (классическая windows.h-ловушка) при добавлении
   следующих модулей.
4. Реальная интеграция AES/ISZ (сейчас — временные заглушки-стабы).
5. `wasm-opt`/`wasm-validate`, реальный запуск в wazero — не проверялись.

6 прогонов sandbox.yml из бюджета, никаких веток/PR/тикетов не создавалось
(чисто разведочный эксперимент, как и планировалось).

## Реальное ограничение ABI, важное для планов (найдено, не архитектурное для f4)

API v6 Observer (не менялось с 2016) не даёт частичного чтения элемента
внутри контейнера - ExtractItem всегда пишет файл целиком в DestPath,
ни stream, ни seek-примитива в протоколе нет. Значит план-пункт про
zran-подобное частичное чтение вложенных архивов для Observer-форматов
принципиально недостижим - только для zip/deflate в plugins/archive.
Сам контейнер (.iso целиком) при этом честно поддерживает random access
через WASI fd_pread/fd_seek поверх ReadAt родительской VFS.

## Часть 9 из N — observer.ini/observer_user.ini + выбор между модулями (28-09-2026)

Перед тем как задавать автору вопрос про скоупинг (см. предположение в
конце части 8 выше), проверено по апстриму: у API v6 (`ModuleDef.h`,
`ACTUAL_API_VERSION 6`) нет вообще никакого готового механизма чтения
ini — ни в самом ABI модуля, ни где-либо в зависимостях, доступных
модулю. Формат `observer.ini`/`observer_user.ini` целиком на стороне
хоста Far-плагина (`src/plugin/Config.cpp`, обычный
`GetPrivateProfileSection`, ничего специфичного для Observer) — это уже
было отмечено в первом комментарии тикета и подтверждено сейчас читкой
исходников. Там же нашлось, что у самого Observer нет отдельного
механизма приоритета между несколькими модулями: `ModulesController::
OpenStorageFile` просто пробует модули из `[Modules]` по порядку файла,
первый не-`SOR_INVALID_FILE` побеждает. Значит пункты 1 и 2 из списка —
не два архитектурных решения, а один и тот же механизм: упорядоченный
конфиг сам и есть выбор между модулями, отдельно изобретать приоритет не
нужно. Вопрос автору не потребовался.
