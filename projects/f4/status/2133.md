## Анализ (Лунобот-1)

Место: `internal/panel/sort_natural.go`, `naturalCompare`; вызывается только из `sortEntriesAt` в `internal/panel/list.go` (`compareName`, при `fp.SortNumeric`) с `textCompare = newNameComparer()` (`internal/panel/namecompare.go`: `collate.New(language.Und, collate.IgnoreCase, collate.Force)`; сборка `extralite` — `namecompare_extralite.go`, ранги: пробелы < пунктуация в порядке root-коллации `_-,;:!?.…$` < прочие символы < цифры < буквы, последним — `strings.Compare`).

Дефект 1 (жалоба): `splitDigitRuns` даёт имени с цифрой в начале пустой первый текстовый кусок (`"1"` → `["", "1"]`), и `naturalCompare` сравнивает куски по позициям: `textCompare("", "!Backup") < 0`, поэтому любое имя с цифрой в начале встаёт раньше имени с пунктуацией. Тот же класс внутри имени: `"a1"` против `"a!"` → `textCompare("a", "a!") < 0` → `a1` раньше `a!`, а в обычной сортировке по имени, в Far и в Проводнике — наоборот (пунктуация < цифры < буквы).

Дефект 2 (тот же класс, найден при разборе; проверить тестом): `collate.Force` делает текстовые куски, равные без учёта регистра, неравными (`"Track_"` против `"track_"`), и решает регистр, а не число: `Track_2` и `track_10` в настоящей сборке сортируются по регистру. Юнит-тест `TestNaturalCompare` этого не видит — он подставляет `caseInsensitiveTextCompare` (`strings.Compare` по нижнему регистру), а не `newNameComparer`.

2. `sort_natural.go`, `naturalCompare`: на чётном (текстовом) индексе, если `textCompare(runsA[i], runsB[i]) != 0`, вернуть `textCompare(runsA[i]+head(runsA, i+1), runsB[i]+head(runsB, i+1))`, где `head` — первая цифра следующего цифрового куска или `""`, если куска нет. Так `"" + "1"` против `"!Backup"` сравнивается как `"1"` против `"!Backup"` (пунктуация раньше цифры), а равные тексты по-прежнему отдают решение числу. Комментарий к функции — про этот инвариант.
