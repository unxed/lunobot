# f4 #1626 — UI не обновляется при максимизации под GNOME Wayland

- Лог автора: бэкенд `x11` (т. е. XWayland, не нативный Wayland). f4 при 202x59 продолжал рендерить и слать кадры (GUI PERF: ~20 кадров, Dirty 3/56), процесс жив — кадры не доходят до экрана. Скриншот: старая картинка 180x52 в углу, остальное чёрное.
- Подозрение: MIT-SHM путь `vtui` (`x11_shm_unix.go`, `flushImage` в `x11_host.go`); ошибки X молча глотаются в `RunEventLoop` (`WaitForEvent` err → continue).
- 28-09-2026: спросили эксперименты (VTUI_NO_SHM=1, --gui=wayland, другой X11-клиент) — https://github.com/unxed/f4/issues/1626#issuecomment-5869144720
- 28-09-2026: автор — с `VTUI_NO_SHM=1` работает, т. е. виноват MIT-SHM путь.
- 28-09-2026: фикс в vtui — unxed/vtui@a166c2118b41f8e10509de43e9bc6c136dc1c778, приземлён в `lunobot/staging` vtui (`train.py land`). Точную причину на XWayland/mutter не воспроизвести: на Xvfb resize с SHM работает. Что сделано: первый ShmPutImage на каждом новом размере — checked, при отказе сервера — откат на core PutImage (как `VTUI_NO_SHM=1`) + полная перерисовка; `RunEventLoop` больше не глотает X-ошибки (DebugLog), ошибка с major opcode MIT-SHM → тот же откат; checked Attach; образ больше сегмента → откат (раньше строки за концом сегмента молча пропускались); depth окна вместо 24; попутно — `shmId > 0` → флаг `shmReady` (id 0 валиден, из-за этого SHM молча не включался, напр. на CI под Xvfb). Тесты без X: `x11_shm_select_test.go`. Проверено в sandbox vtui: `go test .`/`go vet .` ubuntu, `go vet .` windows/macos; разовый Xvfb-зонд (не в коммите): checked put на 640x400/1616x944/1440x832 проходит, асинхронная BadMatch от ShmPutImage выключает SHM.
- Комментарий автору: https://github.com/unxed/f4/issues/1626#issuecomment-5871837370 (попросили после обновления — развернуть без `VTUI_NO_SHM` и прислать debug-лог).
- Дальше (отдельный шаг): когда поезд vtui вольёт a166c21 в main vtui и будет тег `vX.Y.Z` (паспорт vtui, «Релизы») — поднять `github.com/unxed/vtui` в go.mod/go.sum f4 до этого тега, land в f4 с `Touch: unxed/f4#1626` и «Пробуйте!». До этого состояние `в пути` в TRIAGE условно: в f4 фикса ещё нет. Если по новому логу откат сработал — искать реальную ошибку XWayland (она будет в логе); если откат не сработал (ошибок нет, а кадры пропадают) — SHM на XWayland теряет кадры молча, тогда вариант — выключать SHM под XWayland (детект по `XWAYLAND` extension / `WAYLAND_DISPLAY`).
