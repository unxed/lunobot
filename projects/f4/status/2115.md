### Общий метод аудита (шаги 4, 5, 6)

1. Зафиксируй проверяемый коммит: `gh api repos/<репозиторий>/commits/<ветка> --jq .sha` (f4 — `main`, dn — `main`, mcommander — `master` upstream `blue-panels/mcommander`). Все ссылки на код — permalink на этот sha.
2. Список ID раздела: `grep -oE '^\| [KCPBTD]-[0-9]+' docs/FAR2L_COMPAT.md` в клоне f4 (строки примера в разделе 9 — внутри блока кода, их не бери: K-01, K-10, T-08 там повторяются).
3. По каждому ID одна строка отчёта в формате раздела 9: `| ID | Result | Env | Note |`. `Result`:
   - `pass` — только с доказательством: тест проекта, который проверяет именно это (имя теста + ссылка на зелёный прогон CI на этом sha), или код, по которому поведение однозначно (permalink + 1 фраза);
   - `fail` — кода нет или он делает другое (permalink на место, где должно быть, или «не найдено: искал `<что>` в `<где>`»);
   - `partial` — часть требования есть (что есть, чего нет);
   - `N/A` — у менеджера нет этой функции (встроенный терминал, редактор, плагины) — с причиной;
   - `unknown` — доказательства нет ни в тестах, ни в коде (нужна ручная проверка в среде E1–E7). `unknown` — не `pass`. Список всех `unknown` — отдельным абзацем в конце отчёта «нужна ручная проверка».
   Локальных сборок и тестов нет; если хочешь динамическую проверку — только прогон CI проекта (песочница f4 `sandbox.yml`, `dn.yml`/pty-скрипты dn, `ci-sandbox.yml` форка mcommander), ссылку на прогон — в `Note`.
4. Каждый `fail`/`partial` — тикет в репозитории проекта (один тикет на ID или на группу ID с одним местом в коде). Заголовок: `far2l compatibility <ID>[, <ID>]: <коротко>`. Тело: цитата требования, ссылка на строку спеки (`https://github.com/unxed/f4/blob/1a52c966c27938d65d35b5a6c7d45cb88661e20d/docs/FAR2L_COMPAT.md#…`), доказательство, ожидаемое поведение, ссылка на unxed/f4#2115. Без `Fixes`/`Closes`. Перед созданием поищи дубль: `gh api 'repos/<репозиторий>/issues?state=all&per_page=100'` и по ключевому слову; есть — ссылка на него в `Note`, новый не заводи. Номер тикета — в `Note`.
5. Отчёт части — один комментарий в unxed/f4#2115: заголовок `Аудит <проект> @ <sha8>, FAR2L_COMPAT 0.1, раздел <N> (<буква>)`, таблица, список тикетов, абзац «нужна ручная проверка». Готово, когда комментарий есть и все тикеты заведены; в status — строка со ссылкой на комментарий.
6. Последняя часть аудита проекта — сводка: уровень, которого проект достигает сейчас по разделу 8 (с `unknown` считать как не-`pass`), и строка заявки по разделу 9 — комментарием в unxed/f4#2115.

### Шаг 8 — набор самопроверки (`tools/far2lcompat` в f4, Go)

Идея: программа сама играет роль терминала — запускает менеджер в своём PTY и видит всё, что он шлёт.
- **8a.** Скелет: `far2lcompat record -- <команда менеджера>` запускает команду в PTY 80×25, отвечает на `CSI 5 n`, `CSI 6 n`, `CSI c`, через 2 с шлёт `F10` (и `Enter` на подтверждение), печатает найденные последовательности включения и выключения (`?2004`, `?9001`, kitty `>`/`=`/`<`, `far2l1`/`far2l0`, `?1000`/`?1006`, `?1004`). Проверяет P-01, P-02 (a), P-03, P-04 и пробу P-05. Готово: unit-тест на «менеджере»-скрипте `sh -c 'printf …; read x'` с ожидаемым выводом; `land`.
- **8b.** `--far2l`: отвечает `ESC _ far2lok BEL`, проверяет `far2l0` при выходе (P-05); `--silent-ext`: не отвечает на запросы с ненулевым ID и проверяет, что менеджер выходит по `F10` за 5 с (P-06).
- **8c.** Пробы хоста: набирает во встроенном терминале менеджера команды из раздела 6 (клавиша показа терминала — параметр, по умолчанию `Ctrl+O`), ответы пишет в файлы `/tmp/fc/T01.out` и сравнивает с ожидаемыми: T-01, T-02, T-03, T-04, T-05 (a), T-07, T-10.
- **8d.** PR в f4: раздел 10 спеки — как запускать набор, какие ID он проверяет; версия спеки 0.2 (или следующая), запись в раздел 12.
