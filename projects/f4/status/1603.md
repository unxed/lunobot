# f4#1603 — Ctrl+C/Ctrl+Z не доходят до интерактивной программы в терминале

## Итог ревизии (Лунобот-3, 28-09-2026)

Код-фикс уже сделан прежними прогонами флота за сегодня, до этого шага;
в этом шаге нового кода не потребовалось — только проверка состояния и
документирование.

### Суть тикета

Репортёр (macOS 12.2, arm64): после запуска интерактивной программы
(`python3` без аргументов, REPL) из командной строки f4 в терминальной
сессии `Ctrl+C`/`Ctrl+Z` перестают действовать — прервать/приостановить
нечем, единственный выход — Command Palette → Close workplace.

### Расследование первого прогона (Лунобот-2, единственный комментарий к тикету)

Гипотеза «глобальный диспетчер хоткеев f4 перехватывает Ctrl+C/Ctrl+Z
раньше PTY» — проверена юнит-тестом (мок PTY) и **опровергнута**: байты
`\x03`/`\x1a` долетают до PTY нормально. Вместо этого найден и
задокументирован реальный баг: обёртка managed foreground command
(`internal/panel/frame.go`, OSC 133 C/D) ждёт маркер "D" для сброса
`pf.Executing`, а SIGTSTP (Ctrl+Z) переводит процесс в job-control-stop
без печати "D" — шелл забирает терминал себе, а f4 остаётся зависшим в
`pf.Executing == true` навсегда (`IsPtyBusy()`/`TerminalOwnsKeyboard()`
не сбрасываются, панели не возвращаются). План на будущее: (1) реальный
эксперимент с настоящим PTY на Linux/macOS, (2) debounced-детект стопа
через `TIOCGPGRP`/`IsBusy()` независимо от маркера "D".

### Что сделано после этого (сегодня же, до текущего шага, `lunobot/staging`)

Четыре коммита, все с трейлером `Touch: #1603`:

1. `05d33a43` — «confirm the D-marker/job-control gap behind #1603 with a
   real PTY»: вынес обёртку managed foreground command в
   `terminal.ManagedForegroundCommand` (одна точка правды вместо двух
   копий), добавил тест на реальном PTY (без моков) — реальный bash +
   job control + реальный Ctrl+Z в PTY master, подтвердил механизм из
   расследования выше.
2. `f132d40a` — «debounce PTY.IsBusy() to detect job-control stops (#1603,
   part 2)»: сам фикс — `pollManagedExecutionDebounce` в
   `internal/panel/frame.go`, вызывается раз в кадр из `Show()` перед
   вычислением `IsPtyBusy()`. Переиспользует `TIOCGPGRP`-проверку
   `PTY.IsBusy()`, задебаунсенную против гонки сразу после старта команды
   (`managedExecStartGuard` 300мс) и против одиночных всплесков
   (`managedExecIdleDebounceStreak` 3 подряд опроса). Два теста на
   реальном PTY (позитивный: Ctrl+Z → `pf.Executing` сбрасывается,
   клавиатура возвращается f4; негативный: без Ctrl+Z `pf.Executing`
   остаётся true и в гоночном окне, и после дебаунса).
3. `f23b50b3` — «fix wrong cross-platform premise in the #1603 D-marker
   test»: реальные прогоны трейна #1613 (linux/amd64, linux/arm64,
   darwin/arm64) показали, что исходная посылка теста части 1 (bash
   никогда не печатает маркер "D" после стопа) неверна на всех трёх
   платформах — bash продолжает выполнение `;`-цепочки и печатает "D" в
   пределах миллисекунд после "Stopped" (SIGTSTP останавливает только
   форкнутую job, не сам интерактивный шелл). Тест переписан
   (`TestManagedForegroundCommand_JobControlStopReclaimsTerminal`) на
   платформонезависимый сигнал — `PTY.IsBusy()` уходит в false и
   стабильно остаётся false. Сама логика дебаунса из части 2 не менялась
   и остаётся верной как backstop, независимый от маркера.
4. `9be9ecf7` — «exclude the #1603 real-PTY test from the Windows build»:
   `internal/terminal/managed_exec_test.go` использует `p.Master`,
   которого нет в Windows PTY (ConPTY) — раньше файл ломал компиляцию
   всего пакета `internal/terminal` на windows/amd64 (не только новый
   тест — весь пакет терял покрытие). Добавлен `//go:build !windows` по
   образцу уже существующих `pty_cloexec_test.go`/`pty_diag_unix_test.go`.

Функционально фикс закрывает и Ctrl+Z (прямая причина зависания), и
объясняет вариант (a) из плана расследования — «Ctrl+C тоже не работает»
воспринимался пользователем так именно из-за уже зависшего состояния
после неудачного Ctrl+Z, а не из-за отдельной проблемы с SIGINT. Пункт
плана (b) (отдельный термиос-нюанс Darwin) прогонами f23b50b3 на
darwin/arm64 не подтверждён отдельно — дебаунс-фикс верен на всех трёх
проверенных платформах одинаково.
