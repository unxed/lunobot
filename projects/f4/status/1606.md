# f4#1606 — портировать патчер ap на Go для vtvibe

## Сделано (лендинг в `lunobot/staging`, коммиты `9e85a76c`, `ab7f3d8a`)

Новый самостоятельный пакет `internal/vtvibe/ap` (не `internal/appatch` —
решение принято по `docs/VTVIBE.md` §16-17 в самом f4: там уже расписана
структура `internal/vtvibe/ap/{parse.go,apply.go,tx.go}` и `Patch`/`Hunk`/
`Plan`/`Apply` для будущей интеграции; `internal/vtvibe/ap.go` уже
существовал раньше и делает detection/extraction патча из ответа модели
(`ExtractPatch`), новый пакет — соседняя, независимая часть: формальный
парсер + движок применения).

Перенесена дословно логика `github.com/unxed/ap` `implementation/ap.py`
(2109 строк) целиком, не только REPLACE:
- парсер (`parse.go`): заголовок `AP x.y`, дрейф ID, алиасы директив,
  markdown-фences, эвристики восстановления (пропущенный Action Directive,
  пропущенный `snippet`, contextual CREATE, implicit file creation);
- поиск (`search.go`): `smart_find` (hybrid search — мягкое начало/жёсткий
  хвост, эвристика декоративных префиксов), fuzzy-подсказки, частичные
  совпадения строки;
- структурный анализ (`structure.go`): подсчёт глубины скобок с
  игнорированием строк/комментариев, `scope_end`, nesting guard для
  INSERT_AFTER/BEFORE, reindent;
- движок (`apply.go` + `modify.go`): REPLACE/DELETE/INSERT_AFTER/
  INSERT_BEFORE/CREATE(файл и директория)/RECREATE/RENAME, contextual
  file/dir DELETE, идемпотентность по каждому режиму, self-written-text
  tracking (`dirty regions`), LOCATOR_CONSUMED, multi-pass retry,
  structural sanity warning, эвристика редундантного префикса проекта в
  пути (`resolvePathPrefix`), path traversal guard;
- отчёты (`report.go`, `errors.go`): `afailed.md` (для модели) и
  `afailed.ap` (машинный повтор проваленных модификаций), коды ошибок 1:1
  с оригиналом (включая нарочно нестандартный `snippet_tail_NOT_FOUND`).

Перенесены один-в-один все 45 кейсов `implementation/cases.py` (c01-c46,
без c19 — как и в оригинале) в `cases_test.go`, таблично, с тем же
раннером (`runAPCase` = `run_case`), той же семантикой ассертов
(`expect_status/error/files/unchanged/missing/stdout/md`).

**Проверено в CI (`sandbox.yml`, не локально):**
- `go test ./internal/vtvibe/ap/... -v` — 45/45 на ubuntu-latest,
  windows-latest, macos-latest (одно расхождение по ходу работы: кейс
  c28 создаёт новый файл без объявленного режима перевода строки, поэтому
  по спеке §2.4 патчер берёт `os.linesep` — тест поправлен, чтобы сверяться
  с `osLineSep()`, а не жёстко зашитым `\n`; это не баг движка, тот же
  эффект есть и в референсной Python-реализации на настоящей Windows);
- `go vet ./internal/vtvibe/...` — чисто;
- `go build ./...` (весь модуль f4) — собирается;
- `go test ./internal/vtvibe/ap/... -cover` — 73.4% покрытия.

## Сделано (3/N, лендинг в `lunobot/staging`, коммиты `02955b5a`, `ceb941c5`)

При старте этого шага обнаружилось, что раздел «Осталось» п.1 ниже уже
устарел: параллельно другой прогон флота landing-ом `02955b5a`

cases_test.go`) уже перенёс 19 из 75 кейсов `implementation/run_tests.py`

hand-written Go-литералы (в том же стиле, что и `cases_test.go`), не как
embed-фикстуры: RENAME (файл+директория, автосоздание родительских
директорий, идемпотентность), bare-directory CREATE, whole-file/
whole-directory DELETE, mixed atomic delete, «create over an existing
directory», `35_safe_create_empty`/`36_safe_create_fail`,
`16_empty_actions`/`17_error_file_not_found`/`20_error_path_traversal`,
и все шесть tolerant/strict-кейсов `61`–`66`. Эта работа не была
отражена в `status/1606.md` на момент начала данного шага — правка
задним числом не вносилась, эта секция фиксирует находку как есть.

Оставшиеся 56 из 75 кейсов TESTS перенесены в этом шаге —
`internal/vtvibe/ap/run_tests_test.go` (коммит `ceb941c5`, `land` в
`lunobot/staging`, вершина `eef53900`): вся базовая механика REPLACE,
все `*_NOT_FOUND`/`AMBIGUOUS_MATCH` ошибки, range-локаторы, набор
anchor/heuristic-resolution кейсов, CRLF/CR (включая явную директиву
`newline`), варианты идемпотентности, RECREATE, boundary anchors
`^`/`$`, multipass retry (`75`). В отличие от `legacy_cases_test.go`,
здесь патчи работают с настоящими исходниками (C++-сниппет, несколько
Python-модулей, JS-файл, файлы с настоящими CRLF/CR) — вручную
перепечатывать их в Go-строки означало бы риск немой опечатки при
транскрипции, которую не поймала бы даже проверка диффом с эталоном.
Поэтому эти 56 кейсов оформлены как `//go:embed testdata/reftests`
(байт-в-байт копия `implementation/{patches,src,expected}/` из
`github.com/unxed/ap`, тот же автор, что уже был источником всего
перенесённого движка) плюс Go-порт `run_positive_test`/
`run_negative_test` — те же ассерты (статус, файловый диф, атомарность
незатронутых файлов при провале, проверка `fuzzy_matches` в контексте
ошибки `SNIPPET_NOT_FOUND`), управляемый таблицей из 56 строк.

Не перенесено намеренно: `generate_test_patches()` самого
`run_tests.py` (его вывод уже байт-в-байт совпадает с тем, что
закоммичено в апстриме — сверено перед копированием фикстур, копировать
код генератора незачем) и CLI-механика `--update-expected`/JSON-отчёта

1. ~~**75 кейсов `implementation/run_tests.py`/`TESTS`**~~ — **сделано**,
   см. секцию «Сделано (3/N, ...)» выше: все 75 перенесены
   (19 в `legacy_cases_test.go` + 56 в `run_tests_test.go`). Уточнение
   к прежней формулировке этого пункта: `scope_end` на деле — не часть

   в `run_tests.py`. Отдельного TODO по нему нет.
2. **Интеграция в vtvibe** (сам тикет явно говорит, что это отдельный
   следующий шаг): `docs/VTVIBE.md` §17 описывает `Hunk`/`Patch`/`Plan`/
   `Apply` с полем `Status` (`StatusOK`/`StatusAmbiguous`/...) для экрана
   ревью патча — это более богатый API поверх того, что уже есть в
   `internal/vtvibe/ap` (`Apply(patchFile, projectDir, Options) *Result`
   работает с текстом целиком, а не по-хунково с возможностью
   включить/выключить). Нужно решить: (а) добавить в `ap` пер-ханковый
   отчёт (какие модификации к какому файлу применились/пропущены) — этого
   сейчас в `Result` нет, есть только agregate `FailedFiles`; (б) написать
   поверх `Hunk`/`Plan`/`Apply` уже в `internal/vtvibe/` (или прямо в
   `internal/vtvibe/ap/`, если Hunk-обвязка тоже туда), которые
   вызывают текущий `ap.Apply`/`ap.Parse` и раскладывают результат по
   файлам для экрана ревью.
3. Текущий `ap.Apply` — стандартная файловая система (`os.*`), не VFS.
   `internal/vtvibe` уже использует `memtree.go` — надо решить, нужен ли

   как это делает Python-эталон. Не решал этот вопрос — не было нужно
   для текущего шага (пакет самостоятельный, тестируется через
   `t.TempDir()`).
4. Покрытие 73.4% — ниже цели 80% по умолчанию (LUNOBOT.md §7.4), но это
   не обязательно делать раньше остального в очереди f4 — просто к
   сведению, кто будет поднимать общее покрытие пакета позже.

## Структура

```
internal/vtvibe/ap/
    types.go       PatchData/FileChange/Modification, канонические ключи
    util.go        мелкие хелперы (сплит строк, normalize, resolveDirectiveKey)
    parse.go       Parse() — разбор формата
    search.go      smartFind, findTargetInContent, fuzzy/partial diagnostics
    structure.go   скобочная глубина, scope_end, nesting guard, reindent
    errors.go      ErrCode/AppError, fixHints
    report.go      afailed.md/afailed.ap
    fsutil.go      pathExists/securePath/resolvePathPrefix/detectLineEndings
    apply.go       Apply()/Options/Result, движок по FILE-блокам
    modify.go      применение одной модификации (самая длинная функция)
    cases_test.go  45 кейсов из cases.py + раннер
```

Публичное API: `ap.Parse(text, strict, warn) (*PatchData, error)` и
`ap.Apply(patchFile, projectDir string, opts ap.Options) *ap.Result`.
