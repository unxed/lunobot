# Статус unxed/f4#566 — XDND source под Wine

**Состояние:** `свободен`; шаг исследования завершён 16-10-2026 (Лунобот-2).

## План

1. Выделить source-половину XDND в vtui так, чтобы её можно было запустить с существующим `*xgb.Conn`, окном source и root от Wine; оставить Linux `X11Host` совместимым. Критерий: тесты XDND проходят, API не требует `X11Host` для запуска source.
2. Подключить Wine bootstrap/source в f4 с безопасным OLE fallback; проверить gate `hostmode.Posix()` и штатный OLE на Windows.
3. Проверить end-to-end на Wine/X11 и сохранить обычные drag/drop пути; acceptance — из тикета.

## Исследование шага 1

В текущем `unxed/vtui/x11_xdnd.go` source уже использует задаваемые `srcWindow` и `srcRoot`; методы `startDrag`, `srcMotion`, `srcRelease` и selection handlers работают через `d.conn` и `d.a`. Однако всё состояние находится в `x11Dnd`, у которого также есть `host *X11Host`, входящая XDND target-логика и инициализация через `newX11Dnd(*X11Host)`/`internAtoms()`. Следовательно, источник пока не создаётся из переданных connection/window/atoms независимо от `X11Host`; безопасная граница выделения — отдельный source state/type с уже интернированными atoms, не переписывание работающего протокола.

Код не менялся и поведение не объявляется реализованным. Следующий шаг: выделить source state и его методы, сохранив receiver-side обработчики на `x11Dnd`; затем добавить тесты на предоставленные source window/root/atoms.

## Часть 3, шаг C3t — причина найдена, правка проверяется (17-10-2026 07:18 UTC, Лунобот-1 node 19d3)
- Итог C3s: https://github.com/unxed/f4/actions/runs/39011625648 (зелёный, headSha `87454539`). Во всех замерших итерациях (2, 3, 4, 6) процесс жив, но ВСЕ потоки спят в `NtWaitForMultipleObjects` (read анонимного пайпа Wine = ожидание Go-рантайма), и ровно один поток стоит в `unix_stream_read_generic` (блокирующий read сокета X). CPU стоит (дельта за 2 с — только таймерный поток). То есть замер всего процесса, не жеста.
- Причина: `unxed/libwinescape` `Syscall6` обходит `entersyscall/exitsyscall` (комментарий у `retryEINTR` в winescape.go и docs/threading.md); `wineConn.Read` делал блокирующий read(2) X-сокета → поток держит свой P, первая stop-the-world пауза (GC от аллокаций жеста) ждёт этот P, пока X-сервер что-нибудь не пришлёт. Объясняет C3o (asyncpreemptoff не помог: P не в Go-коде вообще), «встаёт на полпути», 50% частоту и то, что журнал замолкает целиком.
- Правка: локальный коммит `91d3a42` в `/tmp/lunobot-1/work/c-1017-0714/f4` (ветка тоже в `tmp/19d3/f4-566-fix`): `wineConn.Read` ждёт данные через `winescape.Poll` срезами по 10 мс и `runtime.Gosched()` между ними (`waitReadable`, тесты с поддельным poll). Проверки: https://github.com/unxed/f4/actions/runs/39013150571 (vet linux+windows, оба golangci-lint, go test пакета) и Wine-проба 8 итераций с правкой: https://github.com/unxed/f4/actions/runs/39013152973 (ожидание: `drop landed` 8 из 8).
