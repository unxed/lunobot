# unxed/f4#2162 (D-05) — план

## Корень

В `internal/panel/frame_dragdrop.go:240` метод `HandleDrag` выполняет диспетчеризацию внешнего Drag and Drop в следующем порядке:
1. `internal/panel/frame_dragdrop.go:255` — вызов `pf.cmdLineDropTarget(ev)`. Если курсор над командной строкой, событие забирает она.
2. `internal/panel/frame_dragdrop.go:258` — вызов `pf.terminalDropTarget(ev)`.
3. `internal/panel/frame_dragdrop.go:262` — если терминал не обработал сброс (`handled == false`), управление переходит в `pf.resolveDropTarget(ev.X, ev.Y)`, и файлы копируются в файловую панель под курсором.

Непосредственная причина бага:
В `internal/panel/frame_dragdrop_term.go:121` функция `terminalDropTarget` немедленно завершает работу, если в терминале нет программы, подписанной на DnD:
```go
if tv == nil || !tv.DropBound() {
    return vtui.DropNone, false
}
```
Из-за `handled = false` сброс файлов на область терминала без запущенного DnD-клиента ошибочно уходит в панель или игнорируется.

Аналогично для nested DnD из внешнего far2l: в `internal/panel/frame_dragdrop_nested.go:111` метод `offerIsForTerminal` возвращает `false` при `!tv.DropBound()`, из-за чего в `ReceiveTerminalOffer` (`internal/panel/frame_dragdrop_nested.go:53`) оффер уходит в `dropTerminalOffer` (`internal/panel/frame_dragdrop_nested.go:68`) для копирования в панель.

## Сравнение с 5b53c848

Коммит 5b53c848 (`frame.go +12/-5`, `frame_dragdrop_term.go +26/-1`, `issue2049_test.go +25/0`) выбрал верное направление: в `terminalDropTarget` при отсутствии `DropBound()` пути нормализуются, экранируются под shell и отправляются в активный PTY с учетом `BracketedPasteMode`.

Что подход 5b53c848 упустил:
1. Защита от `DropMove`: если внешний источник передает действие Move, терминал обязан возвращать `DropCopy`. Возврат `DropMove` приведет к тому, что приложение-источник удалит оригинальные файлы после вставки текста.
2. Случай `hiddenConsoleCommandLineOwnsInput()`: как и при клике правой кнопкой в `frame.go`, ввод может принадлежать скрытой консоли панели.
3. Проверка на пустой список валидных путей и отсутствие активного PTY (`GetActivePTY() == nil`): событие должно поглощаться (`handled = true`), чтобы не происходило ложного проваливания в панели.

Вывод: подход 5b53c848 пригоден как основа, но требует доработки граничных условий.

## Изменения

1. Функция экранирования:
   - В коде командной строки пути нормализуются через `NormalizeExternalDropPath` (`internal/panel/frame_dragdrop.go:68`), затем вызывается `pf.InsertPathToCmdLine(p)` (`internal/panel/frame_dragdrop_cmdline.go:56`). Сама реализация `InsertPathToCmdLine` и функция экранирования для шелла находятся в `internal/panel/frame.go` (файл отсутствует в предоставленном наборе).
   - Вызвать `InsertPathToCmdLine` напрямую для терминала нельзя, так как она пишет в буфер виджета `CmdLine`. Однако хелпер экранирования аргументов шелла (кавычки/бэкслеши для пробелов и спецсимволов) необходимо переиспользовать при форматировании строки путей перед отправкой в PTY.

2. Логика `terminalDropTarget` (`internal/panel/frame_dragdrop_term.go:119`):
   - Проверить `tv == nil` и попадание координат в границы `tv.GetPosition()` (`internal/panel/frame_dragdrop_term.go:126-129`).
   - Если координаты перекрыты видимой панелью (`internal/panel/frame_dragdrop_term.go:123`, `resolveDropTarget`), вернуть `vtui.DropNone, false` (приоритет панели сохраняется).
   - Если `tv.DropBound() == true`: сохранить исходное поведение (`internal/panel/frame_dragdrop_term.go:136-154`) — передача через `newDropFileSource` и `tv.OfferDrop`. Это поведение НЕ должно меняться.
   - Если `!tv.DropBound()`:
     - Разрешенное действие: если `ev.Allowed` не содержит `DropCopy` и `DropMove`, вернуть `DropNone, true`. При наличии `DropMove` или `DropCopy` всегда заявлять и возвращать клиенту только `DropCopy`.
     - На фазе `ev.Phase != vtui.DragDrop` вернуть `vtui.DropCopy, true`.
     - На фазе `ev.Phase == vtui.DragDrop`:
       - Нормализовать пути через `NormalizeExternalDropPath` (`internal/panel/frame_dragdrop.go:68`).
       - Пропустить пустые; экранировать каждый оставшийся путь для шелла и объединить через пробел.
       - Если строка пуста, завершить с `DropCopy, true`.
       - Если `pf.hiddenConsoleCommandLineOwnsInput()`, передать текст в `pf.pasteHiddenConsoleText(...)`.
       - Иначе получить `pty := pf.GetActivePTY()`. Если `pty != nil`: при `tv.BracketedPasteMode == true` обернуть текст в `\x1b[200~` и `\x1b[201~`, затем записать в PTY через `pf.WritePTY(pty, data)`.
       - Вернуть `vtui.DropCopy, true`.

3. Видимость панелей:
   - Панели скрыты (`!pf.ShowPanels`): `resolveDropTarget` возвращает `false` (`internal/panel/frame_dragdrop.go:193`), весь экран терминала принимает дроп как вставку текста.
   - Панели видны: дроп над панелью уходит в панель; дроп над открытыми участками терминала вставляет текст.

4. Офферы из внешнего far2l (`frame_dragdrop_nested.go`):
   - `ReceiveTerminalOffer` оперирует потоками VFS (`far2ldnd`), а не локальными путями хоста. Без `DropBound()` вложенный терминал не может принять оффер как пути. Оставить текущую логику `offerIsForTerminal`, не допуская ложной вставки бинарных данных в PTY.

## Риски

1. Потеря файлов при действии Move: если вернуть `vtui.DropMove`, файловый менеджер хоста удалит файлы после дропа в терминал. Защита: жестко возвращать только `DropCopy`.
2. Рассинхронизация экранирования: если правила экранирования путей для шелла в терминале разойдутся с командной строкой Far, команды при запуске упадут с синтаксической ошибкой. Необходимо использовать общую функцию экранирования.
3. Отсутствие PTY: запуск дропа до инициализации PTY не должен приводить к панике или проваливанию в файловую панель.
