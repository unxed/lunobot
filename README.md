# Лунобот

Лунобот ведёт задачи, ветки и CI через отдельный учётный репозиторий. Рабочий процесс описан
в [LUNOBOT.md](LUNOBOT.md); ниже — короткая инструкция для подключения своего проекта.

## Подключить проект

1. Создайте **свой учётный репозиторий**: в общем `unxed/lunobot` у вас может не быть права
   записи. Для закрытого проекта учётный репозиторий тоже обязательно должен быть закрытым.
   Например, после проверки доступа через общесистемный `gh`:

   ```sh
   git clone https://github.com/unxed/lunobot.git lunobot-accounting
   gh repo create OWNER/ACCOUNT --private --source=lunobot-accounting --remote=accounting --push
   git -C lunobot-accounting remote rename origin upstream
   git -C lunobot-accounting remote rename accounting origin
   ```

   Подставьте свои `OWNER/ACCOUNT`. Для исключительно открытых проектов можно заменить
   `--private` на `--public`; в публичной копии нельзя хранить даже ссылки, названия тикетов,
   логи или состояние работ закрытого проекта. В закрытой копии `pages.yml` по умолчанию не
   публикует пульт, чтобы случайно не открыть эти сведения. Там также выключен
   автоматический `janitor.yml`: бот запускает `janitor.py` локально через авторизованный
   общесистемный `gh`. Локальный `python3 status.py` работает так же.

2. В [`OWNER_QUEUE.md`](OWNER_QUEUE.md) укажите `Автор доверенных тикетов: <login>`:
   только тикеты этого пользователя в учётном репозитории бот считает прямыми поручениями.
   В своей копии оставьте в `projects/INDEX.md` только проекты, которыми бот должен
   заниматься; ненужные каталоги примеров удалите. Создайте `projects/<slug>/` и его `PROJECT.md`:

   ```md
   # <slug>

   - Код: https://github.com/<owner>/<repo>
   - Задачи: тикеты и PR этого репозитория
   - PR: туда же, ветка -> PR -> мерж в main
   - Зависимости: нет
   - Язык общения: по языку автора тикета
   - Режим публикации: PR
   - Отладка GitHub CI: да|нет
   - Диагностический workflow: sandbox.yml
   - Особенности: команды CI, платформы и ограничения проекта
   ```

   Рядом создайте `DISPATCH.md`, `CI.md`, `BRANCHES.md`, `TRIAGE.md` и `status/.gitkeep`;
   скопируйте только заголовки и формат из проекта-примера, но не активные записи.
   `Режим публикации: PR` позволяет начать без staging и поезда: отдельная ветка, PR и
   обязательный CI проекта. Если ваш проект уже настроен на `lunobot/staging` и `quick.yml`,
   можно выбрать `Режим публикации: поезда`. Перед первой работой Лунобот заполнит
   `TRIAGE.md` по открытому списку, а `check_triage.py` проверит его полноту.

3. Проверьте доступ учётной записи бота через **общесистемный** GitHub CLI, а не через
   изолированный shell:

   ```sh
   gh auth status
   gh api user --jq .login
   gh repo view OWNER/ACCOUNT --json nameWithOwner,viewerPermission
   gh repo view OWNER/PROJECT --json nameWithOwner,viewerPermission
   ```

   Для закрытого проекта эта учётная запись должна иметь доступ к репозиторию, право создавать
   ветки и PR, мержить их и запускать нужные Actions. Не кладите PAT, ключи или секреты в
   `PROJECT.md`, учётный репозиторий или комментарии: используйте системный keyring `gh` и
   секреты GitHub Actions.

4. В рабочем репозитории оставьте обязательные CI-гейты. `Отладка GitHub CI: да`
   означает узкие проверки на подходящем GitHub Actions-раннере; настройте указанный в
   паспорте диагностический workflow (для f4 это `sandbox.yml`). При `нет` быстрые изменения можно
   проверять локально; обязательный CI перед мержем остаётся. Если настройки нет, бот
   выбирает CI для компилируемого проекта или долгих/сложных тестов, иначе — локально.

5. Передайте боту цель запуска (подставьте свой репозиторий):

   ```text
   Ты — Лунобот. Учётный репозиторий: OWNER/ACCOUNT.
   Через общесистемный gh проверь доступ и прочитай LUNOBOT.md из main учётного репозитория.
   Следуй инструкции и работай по projects/INDEX.md.
   ```

   Claude Sonnet/GPT Terra и сильнее получают номер 1, более лёгкие модели — номер 2.
   На одном узле запускайте не более одного координатора каждого номера. Для закрытой копии
   инструкция читается через авторизованный `gh api`, не через публичный raw-URL.

Для закрытого проекта безопасный минимум — закрытый учётный репозиторий, отключённая
публикация пульта и проверка доступа `gh` к обоим репозиториям до первого захвата.

## Новое поручение без перезапуска бота

В конце [`OWNER_QUEUE.md`](OWNER_QUEUE.md) добавьте блок по образцу: уникальный id,
`Адресат: любой` (либо `Лунобот-1`/`Лунобот-2`), `Проект: <slug>` или `учёт`,
конкретное поручение и `Состояние: свободно`. Первый подходящий бот после обновления клона
запишет там же «взял в работу», а по фактическому завершении — «сделал» со ссылкой на
результат. Запись о блокировке остаётся в том же файле; повторно запускать бота не нужно.
Можно вместо этого создать issue в своём учётном репозитории от указанного доверенного
автора. Бот проверяет такие issues в начале сессии и после каждого полного круга; выполненный
тикет он отмечает в очереди и закрывает. Запрошенную таким тикетом правку инструкции
`LUNOBOT.md` он вправе внести прямо в `main` учёта без отдельного PR.
